# Публикация `dev` → `main`

После проверки изменений и коммита в `dev`, из корня любого из двух worktree:

```sh
./scripts/publish_main.py
```

Скрипт лежит в `dev`, поэтому из worktree `main` укажи путь к нему:

```sh
../Term-Paper/scripts/publish_main.py
```

Нужны Git, Python 3.12 и `uv`. Скрипт использует только стандартную библиотеку,
не устанавливает зависимости проекта, не запускает обучение и не пересобирает PDF.
Обе ветки должны иметь существующие отдельные worktree и быть чистыми. Скрипт
сам находит их через Git; переключений веток, stash, reset и удаления worktree нет.

## Что делает команда

Источником служит зафиксированный `dev`. Скрипт находит второй родительский коммит
последней публикации в `main` и переносит изменения относительно него. Список уже
опубликованных файлов в `main` задаёт разрешённый состав. Частные каталоги, кеши,
инструкции агентам, инструменты публикации и `Parametric-Adaptation-Methods-RAG_uni.pdf`
не публикуются, даже с `--include`.

Публичный `.gitignore` остаётся из `main`. Различия в `README.md` и
`experiments/README.md` сохраняются при трёхстороннем объединении текста; конфликт
останавливает команду до изменения `main`. Содержательные исправления других файлов,
сделанные только в `main`, нужно сначала перенести в `dev`.
Фактические исправления публичных README также сначала вноси в `dev`: скрипт
сохраняет их отличия как слой публикации и не может определить смысл правки.

Команда печатает полный список изменяемых путей, проверяет состав дерева, основной
PDF и синтаксис изменённых Python/JSON-файлов. Она не заменяет проверку результатов
экспериментов и визуальную проверку PDF перед коммитом в `dev`.

Публикация создаётся с двумя родителями: прежний `main` и выбранный коммит `dev`.
Сообщение содержит только заголовок `main update`; другой заголовок можно передать
через `--message 'update paper'`. Пустые публикации не создаются. Затем **обе ветки**
отправляются в `origin` одним атомарным push без force. История `dev` становится
доступна через `main`; фильтрация относится только к текущему публичному дереву.

## Предпросмотр и изменения состава

```sh
./scripts/publish_main.py --dry-run
./scripts/publish_main.py --include src/new_module.py
./scripts/publish_main.py --skip local-note.txt
./scripts/publish_main.py --allow-deletions
```

`--dry-run` не меняет refs, рабочие файлы или удалённые ветки и не обращается к сети.
Если `dev` грязный, он показывает только зафиксированное состояние и предупреждает
об этом. Реальная публикация грязного `dev` запрещена.

Новые файлы за пределами приватных каталогов требуют явного выбора `--include PATH`
или `--skip PATH`. Пути задаются относительно корня репозитория, по одному файлу;
параметры можно повторять. Отсутствующие в `main` рабочие материалы не возвращаются
автоматически. Удаления из `dev` затрагивают только уже опубликованные файлы и требуют
`--allow-deletions`; при переименовании также укажи новый путь через `--include`.
Сначала посмотри план через `--dry-run`, затем разреши нужные изменения состава.

`--no-push` оставляет публикацию локально. Следующий обычный запуск отправит её,
не создавая дубликат. Если push завершился ошибкой, локальный коммит сохраняется:
исправь причину и повтори команду. Если удалённая ветка ушла вперёд или разошлась,
скрипт остановится; обнови сведения через `git fetch origin` и согласуй историю вручную.
Команда никогда не делает force push. Последние исходные SHA и состояние операции
записаны в `publish-main-last.json` внутри общей Git-директории.

## Проверка скрипта

```sh
uv run --no-project --python 3.12 python -m unittest discover -s scripts/tests -v
```

Тесты работают с временными репозиториями и локальным bare remote. Рабочие ветки
проекта и GitHub они не меняют.
